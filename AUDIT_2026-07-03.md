# Scrappy — Audit de suivi

> Date : 2026-07-03
> Périmètre : revue de code complète (`scrappy/`, `tests/`), hygiène du dépôt, outillage, suivi des questions ouvertes de l'audit du 2026-06-24 (`AUDIT.md`).
> Méthode : trois revues indépendantes (cœur scoring/stockage, connecteurs/CLI/XLSX, hygiène/tests), chaque constat vérifié contre le code avant inclusion. Suite de tests exécutée : **40 tests verts en 0,42 s** (37 lors de l'audit précédent).

## 1. Synthèse exécutive

L'architecture reste saine et conforme à l'ADR : quatre frontières nettes (connecteurs → normalisation/dédup → scoring → présentation), zéro dépendance runtime, connecteurs interchangeables, tests hermétiques et rapides. Le dépôt s'est assaini depuis juin (base SQLite sortie du suivi git, aucun secret commité — historique vérifié).

Trois problèmes de fond dominent cet audit :

1. **Le moteur de matching est calibré pour de l'anglais ASCII alors que la cible est le marché français.** Aucune normalisation des accents : « télétravail », « confirmé », « 7 ans d'expérience » ne matchent jamais les termes internes (`teletravail`, `confirme`, motifs regex anglais). Plusieurs gates critiques — remote hybride, séniorité, plafond d'expérience — sont **silencieusement inopérants sur les offres françaises réelles**. C'est le constat le plus impactant : il fausse le classement que tout le reste de l'outil sert à produire.
2. **La chaîne de collecte peut perdre une collecte entière sur un incident banal.** Réponse non-JSON d'Algolia → crash non attrapé ; dépassement de la borne `range` France Travail en mode standard → HTTP 400 → toutes les offres déjà collectées jetées ; token OAuth jamais rafraîchi → les runs longs (`--time-budget-seconds`) tournent à vide sans message après ~25 min.
3. **Le calcul incrémental « new or changed » — cœur de la proposition de valeur « ne pas retraiter l'inchangé » — est structurellement faux.** Le hash de contenu WTTJ porte sur le hit Algolia brut (champs volatils `_highlightResult`, `_rankingInfo`), et `hash_offer` inclut l'URL, donc deux sources du même job se ré-écrasent mutuellement à chaque run (« ping-pong »). Résultat : re-analyses permanentes et compteurs gonflés.

S'y ajoutent des points de sécurité faciles à corriger (secrets exposés par `repr()` des dataclasses connecteurs, token Apify en query string), des défauts du writer XLSX qui touchent le workflow central de revue (scores écrits en texte → tri Excel faux ; caractères de contrôle non filtrés → fichier illisible), et un outillage absent (pas de CI, pytest non déclaré, `.venv` local cassé, `logics/` désynchronisé des deux derniers commits).

**Verdict** : MVP architecturalement solide, mais dont la fiabilité *sur données réelles françaises* n'est pas encore au niveau de ce que la structure laisse croire. Les correctifs P0 ci-dessous sont pour la plupart petits et localisés.

## 3. Bugs de correction (nouveaux, vérifiés)

Classés par impact décroissant.

### 3.1 Accents non normalisés → gates français inopérants — **critique**
`scoring.py` ne fait que `.lower()` (`_offer_text`, ligne 115), aucune normalisation Unicode. Les termes internes sont sans accents :
- `"teletravail"` (`scoring.py:127, 143-147, 153-154`) ne matche jamais « télétravail » → le statut « substantial remote hybrid » est inatteignable pour une offre FR ; une offre « 4 jours de télétravail » à Lyon est rejetée par le gate localisation.
- `"confirme"` (`scoring.py:179`) ne matche pas « confirmé » → séniorité « unspecified » (6 pts au lieu de 12).
- Même problème pour `"sponsorise"` (`scoring.py:208`) et les motifs d'expérience (cf. 3.2).

**Correctif** : normalisation NFKD + suppression des diacritiques en un seul point (texte d'offre *et* termes). Corrige toute la famille d'un coup.

### 3.2 `_max_required_years` ne parse pas « 7 ans d'expérience » — **critique**
`scoring.py:184-193` : les motifs exigent `experience` directement après `(?:years?|ans)\s+(?:of\s+)?`. La formulation française standard « 7 ans **d'**expérience » échoue (le `d'` + l'accent). Le gate `too_senior_gt_6_years` est silencieusement contourné pour la majorité des offres FR. Aucun test en français n'existe (`test_scoring.py:127-144` ne couvre que « 7+ years of experience »).

### 3.3 Hash de contenu instable → re-analyses permanentes — **critique**
Deux causes qui se cumulent :
- **WTTJ** (`wttj.py:161-163`) : le `content_hash` porte sur le hit Algolia brut, qui contient des champs dépendants de la requête (`_highlightResult`, `_rankingInfo`). La même offre trouvée via deux requêtes différentes est marquée « changed » et re-scorée à chaque run. À hasher : les champs métier extraits, comme le fait déjà `hash_offer` en fallback. (Vigilance analogue pour Indeed `indeed.py:130` et France Travail `france_travail.py:188`.)
- **Cross-source** (`storage.py:363-365`) : `hash_offer` inclut `offer.url`. Deux sources du même job ont des URLs différentes donc des hashes toujours différents ; dans `upsert_offer` (`storage.py:164-190`) chaque observation écrase la ligne canonique de l'autre source (« ping-pong »), `new_or_changed_count` est gonflé en permanence, et le `content_hash` stocké devient incohérent avec la colonne `url` (jamais mise à jour). Le test `test_storage.py:94` entérine ce comportement sans le questionner.

### 3.4 Parser YAML : `#` dans une valeur tronque — « C# » devient « c » — **haute**
`profile.py:29` : `line.split("#", 1)[0]` s'applique avant tout parsing, y compris dans les valeurs. `- C#` est parsé comme la compétence `C` — précisément le faux positif que `_term_regex` a été écrit pour éviter. Les tabulations d'indentation sont par ailleurs silencieusement mal comptées (`profile.py:31`). Aucun `tests/test_profile.py` n'existe.

### 3.5 Configuration morte dans `profile.yaml` — **haute**
`examples/profile.yaml` définit `exclusions.hard_terms`, `military_terms`, `allowed_adjacent_terms` et invite à les éditer, mais `scoring.py` ne lit que `downrank_terms` (ligne 75) ; les listes d'exclusion dure/militaire sont codées en dur dans `_hard_exclusion` (`scoring.py:196-203`), avec des termes différents du profil. Éditer ces sections n'a **aucun effet** — violation silencieuse du contrat du fichier de profil. Brancher ou supprimer.

### 3.6 WTTJ : deux crashs non attrapés qui font perdre le run — **haute**
- `wttj.py:207-218` : `json.loads` est dans le `try` mais le `except` ne capture que `(HTTPError, URLError, TimeoutError)`. Une réponse 200 non-JSON (HTML de rate-limiting Algolia, page CDN) lève `json.JSONDecodeError`, non attrapée par `cli.py:146` (`except RuntimeError`) → traceback brut, run laissé en statut `started` en base (`finish_run` jamais appelé), offres des providers précédents perdues (pas d'export). Indeed et France Travail capturent bien cette erreur (`indeed.py:165`, `france_travail.py:239`) — incohérence.
- `wttj.py:118` : `data.get("results", [{}])[0]` → `IndexError` si l'API renvoie `{"results": []}` (le défaut ne s'applique que si la clé est absente).

**Correctif structurel** : une exception dédiée `ConnectorError` normalisant toutes les erreurs connecteur, et `finish_run(..., status="failed")` dans un `finally`.

### 3.7 France Travail : deux modes de défaillance des collectes longues — **haute**
- **Borne `range` non plafonnée en mode standard** : `MAX_RANGE_END = 1149` (`france_travail.py:24`) n'est utilisé que par `_discover_until_deadline` (ligne 124). Le chemin standard (`discover_with_stats` lignes 98-107, `search_page` lignes 142-145) ne plafonne pas : `--max-pages 15 --hits-per-page 150` → page 8 demande `range=1200-1349` → HTTP 400 → `RuntimeError` → le provider est marqué `failed` et **toutes les offres déjà collectées (jusqu'à ~1150) sont jetées**, alors que `DiscoveryResult.error` supporte le résultat partiel.
- **Token OAuth jamais rafraîchi** : `_access_token` est caché à vie (`france_travail.py:246-249`), `expires_in` ignoré (lignes 273-278), 401 ni retenté ni traité (ligne 234). Avec `--time-budget-seconds 3600`, après ~25 min chaque requête 401 est avalée par `except RuntimeError: continue` (lignes 133-134) : la boucle martèle l'API jusqu'à la deadline **sans rien collecter et sans aucun message**.

### 3.8 Faux positifs concrets des gates sous-chaîne — **moyenne**
Au-delà du constat générique de juin, cas vérifiés :
- `"stage"` (`scoring.py:169`) : « early-**stage** startup » ⇒ classée stage, inéligible. Incohérence relevée au passage : `_hard_exclusion` n'inclut pas « stage », donc un vrai stage FR sans le mot « internship » n'est pas hard-exclu.
- `"cdi"` (`scoring.py:159`) : la société « **Cdi**scount » valide le gate contrat.
- `"intern "` avec espace final : « intern » en fin de texte non détecté.
- Négation aveugle : « this is **not a fully remote** role » ⇒ statut « full remote » (`scoring.py:120-122`).
- Contournement militaire trop large : « safety »/« security » n'importe où dans le texte désactive l'exclusion d'une offre explicitement « defense/army » (`scoring.py:199-202`).

**Correctif** : réutiliser `_term_regex` (déjà écrit et testé) dans `_contains_any`.

### 3.9 Défauts de déduplication et de revue manuelle — **moyenne**
- **URL vide fusionne des offres distinctes** : `canonicalize_url("") == ""` et la requête d'existant (`storage.py:156`) teste `canonical_url = ?` sans garde sur vide (contrairement à `dedupe_key != ''` ligne 157). Deux offres sans URL fusionnent, la seconde écrase la première.
- **`save_manual_review` échoue silencieusement sur les offres fusionnées** (`storage.py:318-323`) : ne cherche que dans `offers`, pas dans `offer_aliases`. Noter une offre via son identifiant de source secondaire retourne `False` (« offre inconnue ») alors qu'elle existe.
- `canonicalize_url` ignore la query string (`storage.py:379`) : `?utm_source=...` défait la dédup URL.
- `duplicate_reason` peut être mensongère (`storage.py:391-397`) : annonce « same normalized title/company/location » même quand la fusion s'est faite par URL.

### 3.10 Divers vérifiés — **basse**
- `ScoreResult` `frozen=True` avec des listes (`models.py:21-30`) : `__hash__` généré lèvera `TypeError` au premier hash ; passer à `tuple[str, ...]`.
- Générateur de requêtes épuisé silencieusement après la page 0 dans Indeed (`indeed.py:84-85`) et France Travail (`france_travail.py:98-99`) — WTTJ matérialise correctement la liste (`wttj.py:59`). Latent (la CLI passe une liste), mais piège de signature `Iterable`.
- `_localized` ignore `self.locale` (`wttj.py:148, 278`) : un connecteur `locale="fr"` extrait toujours le contract_type anglais.
- `from_env` France Travail : `float()` sur une variable d'env vide ou « 0,4 » (locale FR) → `ValueError` non attrapée (`france_travail.py:54-56`).
- `avg_score_gain` dilué par les offres « unlocked » à gain nul (`growth.py:106`) ; tri sans départage déterministe par nom (`growth.py:118-121`).
- Migrations décoratives : `SCHEMA_VERSION=3` inséré tel quel, seule `_ensure_column` migre réellement (`storage.py:14, 124-127`) ; aucun test de migration.
- Code mort : chemin scraping HTML WTTJ (`wttj.py:178-254`), test 204 en double (`france_travail.py:228-233`), branche `merged_sources_json` (`storage.py:440-442`).
- `latest_ranked` : N+1 requêtes via `offer_alias_summary` par ligne (`storage.py:299-302`), pas d'index sur `analyses(offer_id)`.

## 4. Sécurité

Le socle est bon : SQL paramétré partout, secrets exclusivement en variables d'environnement, `.env.local` gitignoré, **aucun secret dans l'historique git** (vérifié), XML échappé dans le writer XLSX. Trois points à corriger :

1. **`repr()` des connecteurs fuit les secrets** (vérifié par exécution) : `IndeedApiConnector` expose `api_key` et `apify_token` (`indeed.py:21-31`), `FranceTravailConnector` expose `client_secret` (`france_travail.py:27-39`). Tout log/traceback affichant le connecteur exfiltre les credentials. Correctif une ligne par champ : `field(repr=False)`.
2. **Token Apify en query string** (`indeed.py:195-197`) : finit dans les logs d'intermédiaires. Apify accepte `Authorization: Bearer`.
3. **Clé Algolia hardcodée** (`wttj.py:19-20`) : clé search-only publique, risque faible, mais sa rotation par WTTJ cassera le connecteur avec une erreur réseau générique (aggravé par 3.6).

À noter côté confidentialité : `data/` et `reports/` contiennent des données de collecte réelles synchronisées sur OneDrive (non suivies par git, mais présentes dans le cloud).

## 5. Robustesse réseau et duplication des connecteurs

- **Trois stratégies de retry divergentes** : France Travail gère 429/`Retry-After` (`france_travail.py:234-236`) ; WTTJ retente tous les `HTTPError` indistinctement, y compris 400/403 (`wttj.py:213`) ; Indeed/Apify n'ont **aucun retry** — un timeout transitoire unique fait échouer le provider.
- `--request-interval-seconds` ne s'applique qu'à France Travail (`cli.py:128`), silencieusement ignoré pour les autres ; `--time-budget-seconds` est couplé en dur au nom `"france_travail"` (`cli.py:143`).
- **Pas d'arrêt anticipé de pagination** : les pages 2..N d'une requête sont demandées même quand `nb_pages` indique qu'il n'y en a qu'une (les fixtures de `test_wttj_connector.py:72-84` montrent ce gaspillage).
- **Boucle de découverte copiée-collée trois fois** (`wttj.py:49-83`, `indeed.py:64-93`, `france_travail.py:77-107`) avec divergences accidentelles (matérialisation des requêtes, pagination 0/1-indexée) ; `_result`, `_nb_pages`, `_unique` dupliqués également (`_unique` diverge même entre `cli.py:272-282` et `france_travail.py:373-382` sur la casse).

**Recommandation structurante** : enrichir `base.py` (aujourd'hui deux dataclasses) d'une classe de base portant requête JSON + retries/backoff/`Retry-After` + throttle générique + boucle de dédup/pagination + `_result`. Chaque connecteur ne garderait que `search_page` et le mapping d'items. Corrige d'un coup la moitié des points ci-dessus.

## 6. Writer/lecteur XLSX (`reporting.py`)

Structure OPC minimale valide, base-26 correcte, round-trip testé, et le lecteur gère `sharedStrings` (fichiers re-sauvés par Excel) — bon travail pour du stdlib pur. Trois défauts, dont deux touchent le workflow central « trier et annoter le XLSX » :

1. **Caractères XML illégaux non filtrés** (`reporting.py:229`) : `html.escape` n'élimine pas les contrôles interdits en XML 1.0 (0x00-0x08, 0x0B, 0x0C, 0x0E-0x1F), fréquents dans du texte scrappé (copier-coller Word). Conséquence : fichier qu'Excel refuse d'ouvrir. Filtrer avec `re.sub(r'[\x00-\x08\x0b\x0c\x0e-\x1f]', '', value)`.
2. **Tout est écrit en `inlineStr`, y compris les scores** (`reporting.py:139, 229`) : la colonne `score` est du texte dans Excel — le tri donne « 9 » > « 80 », les filtres numériques ne marchent pas. Écrire les numériques en type `n`.
3. Pas de `xml:space="preserve"` sur `<t>` : espaces de tête/queue et retours ligne normalisés par certains lecteurs. Mineur : `_worksheet_target` (`reporting.py:248`) suppose une cible relative — `KeyError` cryptique sur cible absolue (rare en pratique).

- **Environnement dev irreproductible** : le `.venv` du dépôt est cassé (Python 3.14 sans pip ni aucun paquet) ; pytest n'est déclaré nulle part (`pyproject.toml` sans `[project.optional-dependencies]`) ; aucune section « installation/développement » au README. Aujourd'hui, on ne peut pas lancer les tests en suivant le dépôt tel quel.
- **Pas de CI** (aucun `.github/`), point ouvert depuis juin. Pas de linter/formateur/type-checker institutionnalisé — le `.gitignore` mentionne `.ruff_cache/`, signe d'un usage local non officialisé.
- **`pyproject.toml` incomplet** : `license`, `authors`, classifiers absents ; `dependencies = []` est exact (100 % stdlib, vérifié).
- **`.gitignore`** : n'ignore pas `.env` (seulement `.env.local`), ni `dist/`, `build/`, `*.egg-info`.
- **`logics/` désynchronisé** : dernier commit sur `logics/` du 24-06 alors que deux features ont été livrées depuis ; `task_005` en `In progress` sans statut.
- **Tests** : 40 verts, hermétiques, rapides (0,42 s), ratio ≈ 0,36 — correct pour un MVP. Lacunes prioritaires :
  - aucun `tests/test_profile.py` (la surface la plus fragile du projet) ;
  - aucun texte accentué ni formulation française dans `test_scoring.py` (les bugs 3.1/3.2 passent inaperçus) ;
  - aucun test end-to-end du chemin heureux de `run` (collecte mockée → stockage → scoring → XLSX) ;
  - 1 seul test pour les 300 lignes du writer XLSX maison ;
  - zéro test pour `_hard_exclusion`, `_downrank_signals`, les migrations de schéma, `rescore`.
